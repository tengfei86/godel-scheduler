# 第一章 绪论

## 1.1 研究背景与意义

自 2014 年 Google 开源以来，Kubernetes 已发展成为云原生领域的事实标准容器编排平台，被全球范围内的互联网企业、金融机构与科研机构广泛部署。Kubernetes 通过声明式 API 与控制器模式抽象了底层基础设施，使得开发者可以以统一的方式管理计算、存储、网络资源。而在 Kubernetes 的诸多控制器中，**调度器**（Scheduler）承担着为待运行的 Pod 选择合适 Node 的核心职责，其吞吐量与延迟直接影响整个集群的资源利用率与工作负载响应速度。

Kubernetes 原生调度器（kube-scheduler）采用单实例串行架构，即整个集群中只有一个 kube-scheduler 处于活跃状态处理 Pod 调度请求。这一设计在千节点规模、百级别并发的常规工作负载下运行良好，但在超大规模集群与高并发调度场景中逐渐暴露出瓶颈：

- **吞吐量瓶颈**：kube-scheduler 单进程内部通过一个 activeQ 串行处理 Pod，实测稳态吞吐上限约 300 pods/s，无法满足在线服务大规模弹性伸缩、批量任务快速启动等场景的调度速度要求；
- **延迟抬升**：随集群节点数增长，Filter 与 Score 阶段遍历节点的开销线性上升，P99 调度延迟在 5000 节点规模下明显恶化；
- **单点故障**：kube-scheduler 通过 Leader Election 保证单实例活跃，一旦 Leader 崩溃需要等待 Standby 接管，期间集群完全无法调度。

为应对上述挑战，业界陆续提出了多种分布式调度器改造方案。字节跳动于 2023 年开源的 **Gödel Scheduler**<sup>[?]</sup> 是其中较为完整的实现，它将调度职责拆分到 Dispatcher、Scheduler、Binder 三层，其中 Scheduler 支持多实例水平扩展，通过节点分区（Node Partition）机制将全集群节点划分为若干互不相交的子集，每个 Scheduler 实例只负责其分区内节点的调度决策，从而消除了多实例间的资源竞争。Gödel 在字节跳动内部支撑了 3 万节点级别的生产集群运行<sup>[?]</sup>。

然而，Gödel 架构中的 **Binder 组件仍然是独立的 Deployment**，负责统一执行 Pod 的绑定（Bind API 调用）与冲突处理。这一设计在保持强一致性的同时，也带来了两方面的开销：

- **绑定阶段的串行化瓶颈**：所有 Scheduler 实例的调度决策均需汇聚到 Binder 才能落盘，Binder 的处理能力再次成为整个流水线的天花板；
- **跨进程通信开销**：Scheduler 与 Binder 之间通过 Kubernetes API Server（也即 etcd）进行事件通信，涉及序列化、网络往返、Informer 事件延迟等额外成本。

与此同时，分布式调度器的**一致性保证**始终是绕不开的关键问题。当多个 Scheduler 实例并发工作时，如何确保任一 Pod 在任意时刻至多被绑定到一个节点、如何处理节点分区归属变更引发的边界情况、如何在 Bind API 暂态失败后正确恢复而不残留脏数据，都需要在系统设计层面给出严谨解答。这些问题的答案高度依赖 Kubernetes 底层存储 **etcd** 所提供的原子性保证——包括 Watch API 的一致性视图、Pod 资源的乐观并发控制（`resourceVersion` 语义）、以及 Bind 子资源的原子写入语义。

综上，围绕大规模场景下的分布式 Kubernetes 调度器展开系统性的架构、一致性与性能研究，具有重要的学术意义与工程价值。

## 1.2 国内外研究现状

Kubernetes 调度器的相关研究主要沿三条主线展开：**架构演进**、**批处理与混部**、**大规模一致性**。

**架构演进方向**上，Google 在 2013 年发表的 **Omega** 论文<sup>[?]</sup> 提出了基于共享状态的乐观并发调度模型，为后续分布式调度器奠定了理论基础；Kubernetes 上游社区在此基础上引入了 Scheduling Framework<sup>[?]</sup> 插件化机制，将 Filter / Score / Bind 等阶段解耦；字节跳动的 Gödel<sup>[?]</sup> 与阿里巴巴的 ASI 调度器<sup>[?]</sup> 则分别在 2023 年前后开源了多实例分区调度的完整实现。

**批处理与混部方向**上，华为孵化的 **Volcano**<sup>[?]</sup> 面向 AI/大数据场景引入了 Gang 调度、Session-based 调度、公平共享等特性；阿里巴巴的 **Koordinator**<sup>[?]</sup> 侧重在线离线混部场景，通过 QoS 感知调度、资源超卖机制提升集群整体利用率。这两个项目均延续了 kube-scheduler 的单实例架构，通过在插件层面扩展 K8s 原生调度器实现差异化能力。

**大规模一致性方向**上，学界与业界均意识到分布式调度器需要在多实例并发场景下保持"任一 Pod 至多绑定到一个节点"这一核心不变量。Omega 论文以乐观锁 + 冲突重试的方式给出答案，而工业界的实现（包括 Gödel）则更多依赖 Kubernetes API Server 的事务语义。然而，围绕分区调度器**在节点归属动态变更场景下**的严格一致性保证，公开发表的完整分析仍然罕见。

现有研究的**局限性**主要体现在：

1. Gödel 等分布式调度器的公开评估多聚焦于稳态吞吐指标，缺乏在延迟分位数、绑定成功率、资源开销等维度的系统性对比；
2. Binder 组件的独立部署形态在大规模场景下的开销缺乏定量分析；
3. 面对节点分区归属漂移、跨实例失败回退等边界场景的容错机制未见完整的证明与实现说明。

## 1.3 研究目标与主要贡献

针对上述现状与局限，本文以字节跳动开源的 Gödel Scheduler 为基础，围绕**大规模分布式 Kubernetes 调度器**开展研究，目标包括：

- 系统性梳理分布式调度器的架构组成与基于 etcd 的一致性依赖；
- 针对分区调度场景下的四类典型故障，设计并实现严格保持核心不变量的容错机制；
- 优化 Binder 独立部署带来的跨进程开销，提升大规模场景下的调度吞吐与延迟；
- 通过 KWOK 仿真环境完成 ENO 与主流开源调度器（Gödel、kube-scheduler、Volcano、Koordinator）的多维度性能对比。

本文的主要贡献包括：

**贡献 1：基于 etcd 的一致性容错框架。** 提出了包含节点归属前置校验（Layer 0）、同步重试（Layer 1）、异步 Reconciler（Layer 2）、跨实例回退（Layer 3）的四层容错机制，涵盖了分区归属漂移、Bind API 暂态失败、进程内偶发错误、本地重试耗尽四类典型威胁；给出了核心不变量"任一 Pod 至多绑定到一个节点"的证明要点，明确了每一层如何依赖 etcd 的原子性语义维护不变量。

**贡献 2：进程内 Binder 架构（ENO）。** 提出将独立 Binder 合并进 Scheduler 进程的架构改造，通过 CacheAdapter 桥接层实现 SchedulerCache 的零拷贝共享。相比原有的独立 Binder 部署形态，ENO 消除了 3 步跨进程 API 往返与相应的序列化开销，同时提供 CLI 开关支持在两种部署形态之间无缝切换。

**贡献 3：多调度器大规模评估。** 基于 KWOK 仿真环境搭建了包含 1000 节点与 5000 节点两种规模、两种工作负载共 60 次实验的评估平台，对 ENO 与四种主流调度器（Gödel、kube-scheduler、Volcano、Koordinator）在稳态吞吐、P90/P99 调度延迟、绑定成功率、goroutines 资源开销等维度进行了系统性对比，并公开了完整的实验方法学与原始数据。

## 1.4 论文组织结构

本文共分七章，结构如下：

**第一章 绪论**，即本章，介绍研究背景、国内外研究现状、研究目标与主要贡献，以及论文组织结构。

**第二章 相关工作与背景**，梳理 Kubernetes 原生调度器、Volcano、Koordinator、Gödel 四种代表性调度器的架构与特点，并简要介绍 etcd 的一致性模型与本文关键依赖的原子性语义。

**第三章 分布式 Kubernetes 调度器系统架构**，系统阐述 Dispatcher/Scheduler/Binder 三层架构、节点分区机制、以及基于 etcd 的三步事务写入模型（dispatching → assuming → binding），并配合三张原创系统图分别展示总体架构、Dispatcher 内部流程、单个 Scheduler 内部流程。

**第四章 基于 etcd 语义的一致性容错机制**，是本文的核心章节之一，详细展开四层容错机制的设计、实现与不变量证明。

**第五章 面向大规模场景的架构优化（ENO）**，阐述独立 Binder 到进程内 Binder 的架构改造思路、Cache 零拷贝共享机制、部署形态变化，以及 CLI 开关的可切换性设计。

**第六章 实验设计与评估**，介绍实验环境、工作负载、评估指标，并给出 ENO 与四种基线调度器的对比结果分析。

**第七章 总结与展望**，回顾主要贡献，诚实讨论工作的局限性，并展望后续研究方向。

## 1. 项目一句话

**论文题目**：《基于 etcd 的分布式 Kubernetes 调度器研究与实现》
**格式规范**：北京航空航天大学研究生学位论文撰写规范（2025.3）
**评估**：5 组调度器（a=ENO / b=Gödel / c=kube-scheduler / d=Volcano / e=Koordinator）× 2 规模（s2=1000 节点、s3=5000 节点）× 2 负载（w2=中、w3=高）× 3 重复 = **60 次已完成实验**。

### 两项核心创新（与摘要 / §1.3 严格对齐）

面向分布式调度系统中"**调度-绑定协同效率不足**"和"**绑定阶段容错能力薄弱**"两类共性问题，提出：

**（1）单 Dispatcher、多独立 Scheduler 分布式调度架构（ENO）**
构建"单 Dispatcher 统一分发 + 多 Scheduler 独立并行执行"的协同模型，将绑定执行链路与调度实例同域化，减少跨组件通信与状态同步开销，实现系统吞吐能力随调度实例数近线性扩展。通过共享缓存适配层实现低拷贝状态复用，并引入特性开关保障新旧架构平滑切换与向后兼容。

**（2）分层容错绑定策略**
构建四层容错链路——**节点分区验证（Layer 0，预防层）**、**同步指数退避重试（Layer 1，即时恢复层）**、**异步 Reconciler 队列（Layer 2，后台恢复层）**、**Dispatcher 跨实例回退（Layer 3，全局恢复层）**——形成分布式调度系统中首个结构化的绑定容错模型。

> **对 agent 的意义**：所有章节写作、图表选题、数据分析都应服务于这两项创新的论证。如需引入其他"创新"级别的贡献，先在 T5 一致性 pass 里讨论，不擅自新增。

## 7A. 去 AI 味的写作规范（De-AI-Styling）

> **为什么**：评审与导师能识别 AI 生成文本的典型特征（过度加粗、列表化、排比句式、空泛总结、宣传腔）。论文必须以自然、克制、可核验的学术表达呈现。**本节为硬性约定，违反即需返工**。

### 7A.1 硬性禁令（必改）

| AI 味特征 | 反面示例 | 改法 |
|---|---|---|
| 正文过度加粗 | "**显著提升**了调度**吞吐**" | 正文原则上不加粗；仅术语首次定义与图注/表题关键词允许加粗 |
| 列表化叙述 | 用项目符号罗列本应成段的论证 | 改为段落叙述；仅步骤、参数、清单类内容用列表 |
| "不是 A 而是 B" 句式 | "ENO 不是简单的进程合并，而是架构重构" | 直陈："ENO 将 Binder 合并进 Scheduler 进程" |
| 排比枚举成瘾 | "其一……其二……其三……" | 合并为连贯段落；确需分点时用"首先/随后/最终"以外的自然承接 |
| 空泛总结句 | "为后续研究奠定了坚实基础" | 删除，或替换为具体结论与数据 |
| 宣传腔 | "完美解决""业界领先""极大提升" | 改用可核验的范围与数字（"+6.6%~13.7%"） |
| 万能连接词高频 | "值得注意的是""综上所述""需要强调的是" | 每章合计不超过 1 次；优先用具体承接词（"因此""相比之下""在 s4 场景中"） |
| 互联网黑话 | 赋能、抓手、闭环、生态、纵深、颗粒度 | 换学术表述：支撑、机制、反馈回路、技术路线、粒度 |
| 破折号滥用 | 每段都有"——" | 每千字不超过 2 处 |
| 括号补注过多 | 句中频繁出现"（即 XXX）" | 首次中英对照后不再重复解释 |

### 7A.2 段落与节奏

- 正文以**段落**为主：每节至少两段连续叙述，禁止"小标题 + 项目符号"的骨架式写法（步骤、参数、实验结果枚举除外）；
- 段落长度**参差**（2~8 句），避免清一色的等长段落；
- 每段只讲一个论点，避免反复套用"总—分—总"；
- 长短句交错，避免每句都是长度相近的"标准句"。

### 7A.3 用词与句式

- 优先**具体**：用指标名、数值、符号、场景代号（s3/w3、`bind_throughput_pods`）代替概括性形容词；
- 技术论断用"本文/该机制/实验结果显示"作主语，避免无主语长句堆叠；
- 中英混排规则：术语首次出现中英对照（如"绑定器（Binder）"），此后固定用中文或固定用英文，不随意夹杂；
- 数字与单位全篇统一（pods/s、秒 / ms、节点数写法一致）。

### 7A.4 自查命令（每章提交前必做）

```bash
# 1. 正文加粗密度：每千字 ** 数量应 ≤ 4（表格、图注不计）
grep -o '\*\*' chapters/0X-*.md | wc -l
# 2. 列表行占比：列表行 / 总行数 应 ≤ 15%（步骤与参数表除外）
grep -cE '^\s*([-*]|[0-9]+[.、]) ' chapters/0X-*.md
# 3. AI 高频词与句式扫描（应为空或极少）
grep -nE '值得注意的是|综上所述|需要强调的是|不是.{0,12}而是|赋能|抓手|闭环|奠定.{0,6}基础' chapters/
# 4. 破折号密度：每千字 ≤ 2
grep -o '——' chapters/0X-*.md | wc -l
```

### 7A.5 主观验收三问

逐段自问：

1. 这句话是否**只有在这篇论文里才成立**？能套用到任何论文的句子即为空话，删；
2. 连续三句是否**句式相同**？是则改写；
3. 去掉全部加粗与列表后，论证是否依然完整？否则说明在用排版掩饰内容。

### 7A.6 首版草稿审读结论（2026-09-14）

以"教授视角"通读一版全文后的判断：**技术内核可信、表达层 AI 味重**。工程细节（commit `5767a76c`、`pkg/binder/node_validator.go`、`--enable-embedded-binder` CLI 开关、w2 三次重复 `146/141/145s` vs `156/168/156s`、Coordinated Omission 讨论）编不出来，属真实工作；但骨架规划与文字打磨明显经过 AI 润色，一读能嗅出。定量估计：骨架 AI 参与度 40–60%，文字润色 50–70%，核心技术贡献 <20%。

#### 三处重灾区（**优先重写**）

**（一）摘要**

单段堆砌 7 组精确百分比：`6.6%~13.7% / 13.3%~39.0% / 47.5%~82.0% / 40.7%~91.0% / 97.1% / 61.0% / 100%`。学生自己写不会这么工整。答辩老师最先读摘要，第一印象决定后续基调。

改法：仅保留 2–3 个最核心的数字（例如 P99 延迟降 97.1%、峰值吞吐提升 61.0%），其它移入正文；用不对称的句式重写；允许一些"生涩"的转折而非全都工整过渡。

**（二）各章开头的"§X.1 介绍…、§X.2 讨论…"路线图**

现状：第 3/4/5/6/7 章开头都是同一个模板句式：

> "本章通过 §X.1 介绍 A、§X.2 讨论 B、§X.3 展开 C、§X.4 总结 D。"

五章格式完全对称，是 AI 生成骨架的典型标志。人类作者写引导段更随性、会露怯、会有偏重。

改法：至少 3 章的引导段用不对称的方式重写，可以以问题引入、以场景描述引入、以上一章结论承接。允许"章节路线图"只在必要时保留（例如第 4 章因结构最复杂可保留）。

**（三）段内 (1)(2)(3) 三段式排比**

全文出现 20+ 处，几乎每一处都工整对齐。重点位置：

- 第 1 章 §1.2 "综合来看，现有研究的局限性主要体现在以下三方面"—— 1/2/3 齐飞；
- 第 5 章 §5.1 独立 Binder 开销四点并列：`(1) 序列化开销 / (2) Informer 延迟 / (3) 额外往返 / (4) 资源占用`——最工整、最典型；
- 第 3 章 §3.1 Dispatcher 四模块 / §3.5 三条设计要点。

改法：挑一半打散为段落叙述；保留列表的地方，避免每项都是"名词 + 冒号 + 均等长度描述"的固定结构；有些点可直接融入正文（"绑定阶段每个 Pod 大约 3–10 KB，w3 稳态下 apiserver 每秒完成 1000 次完整序列化循环"是叙述，"（1）序列化 / 反序列化 CPU 开销：..."是排版）。

#### 有作者痕迹（**保留**）

- §6.4.1 挑战自己数据的 w2 分析（"稳态吞吐数值不宜单独作为处理能力的判据"）——最像真作者，AI 通常掩盖不利数据；

**这些不要动**。真实性正来自这些"不完美"的段落。

#### 可能被答辩追问的表述（**弱化或加限定**）

| 现表述 | 风险 | 改法 |
|---|---|---|
| "本文所见分布式 Kubernetes 调度系统中**首个**结构化的绑定容错模型" | "首个"这类最高级最容易被挑战——需证明穷尽了所有公开文献 | 改为"据本文所调研的公开文献所见……"或"面向 Kubernetes 生态的现有分布式调度实现中，尚未见结构化的分层绑定容错模型" |

# 第一章 绪论

## 1.1 研究背景与意义

自 2014 年 Google 开源以来，Kubernetes 已发展成为云原生领域的事实标准容器编排平台，被全球范围内的互联网企业、金融机构与科研机构广泛部署。Kubernetes 通过声明式 API 与控制器模式抽象了底层基础设施，使得开发者可以以统一的方式管理计算、存储、网络资源。而在 Kubernetes 的诸多控制器中，**调度器**（Scheduler）承担着为待运行的 Pod 选择合适 Node 的核心职责，其吞吐量与延迟直接影响整个集群的资源利用率与工作负载响应速度。

Kubernetes 原生调度器（kube-scheduler）采用单实例串行架构，即整个集群中只有一个 kube-scheduler 处于活跃状态处理 Pod 调度请求。这一设计在千节点规模、百级别并发的常规工作负载下运行良好，但在超大规模集群与高并发调度场景中逐渐暴露出瓶颈：

- **吞吐量瓶颈**：kube-scheduler 单进程内部通过一个 activeQ 串行处理 Pod，实测稳态吞吐上限约 300 pods/s，无法满足在线服务大规模弹性伸缩、批量任务快速启动等场景的调度速度要求；
- **延迟抬升**：随集群节点数增长，Filter 与 Score 阶段遍历节点的开销线性上升，P99 调度延迟在 5000 节点规模下明显恶化；
- **单点故障**：kube-scheduler 通过 Leader Election 保证单实例活跃，一旦 Leader 崩溃需要等待 Standby 接管，期间集群完全无法调度。

为应对上述挑战，业界与学界陆续提出了多种分布式调度器改造方案，通过将调度职责拆分到多个组件、多个实例并发执行的方式突破单实例架构的性能天花板。然而，分布式改造在带来吞吐提升的同时，也引入了新的关键问题——**多实例并发场景下的一致性保证**：如何确保任一 Pod 在任意时刻至多被绑定到一个节点、如何处理节点分区归属变更引发的边界情况、如何在 Bind API 暂态失败后正确恢复而不残留脏数据，都需要在系统设计层面给出严谨解答。这些问题的答案高度依赖 Kubernetes 底层存储 **etcd** 所提供的原子性保证——包括 Watch API 的一致性视图、Pod 资源的乐观并发控制（`resourceVersion` 语义）、以及 Bind 子资源的原子写入语义。

综上，围绕大规模场景下的分布式 Kubernetes 调度器展开系统性的架构、一致性与性能研究，具有重要的学术意义与工程价值。具体的分布式调度方案与相关研究进展将在 §1.2 展开。

## 1.2 国内外研究现状

Kubernetes 调度器的相关研究主要沿三条主线展开：**架构演进**、**批处理与混部**、**大规模一致性**。

**（一）架构演进方向。** Google 在 2013 年发表的 **Omega** 论文<sup>[1]</sup> 提出了基于共享状态的乐观并发调度模型，为后续分布式调度器奠定了理论基础；Kubernetes 上游社区在此基础上引入了 Scheduling Framework<sup>[2]</sup> 插件化机制，将 Filter / Score / Bind 等阶段解耦，为第三方调度器扩展提供了框架级支持。

进一步地，为突破单实例架构的吞吐上限，业界陆续提出多实例并发调度的完整实现。其中，字节跳动于 2023 年开源的 **Gödel Scheduler**<sup>[3]</sup> 是目前公开可获得的、较为完整的分布式 Kubernetes 调度器实现：它将调度职责拆分到 **Dispatcher / Scheduler / Binder 三层**，其中 Scheduler 支持多实例水平扩展，通过**节点分区（Node Partition）机制**将全集群节点划分为若干互不相交的子集，每个 Scheduler 实例只负责其分区内节点的调度决策，从而消除了多实例间的资源竞争。Gödel 在字节跳动内部支撑了 3 万节点级别的生产集群运行<sup>[4]</sup>。

然而，Gödel 类分布式调度器架构中的 **Binder 组件仍然是独立的 Deployment**，负责统一执行 Pod 的绑定（Bind API 调用）与冲突处理。这一设计在保持强一致性的同时，也带来了两方面的开销：

- **绑定阶段的串行化瓶颈**：所有 Scheduler 实例的调度决策均需汇聚到 Binder 才能落盘，Binder 的处理能力再次成为整个流水线的天花板；
- **跨进程通信开销**：Scheduler 与 Binder 之间通过 Kubernetes API Server（也即 etcd）进行事件通信，涉及序列化、网络往返、Informer 事件延迟等额外成本。

**（二）批处理与混部方向。** 华为孵化的 **Volcano**<sup>[5]</sup> 面向 AI / 大数据场景引入了 Gang 调度、Session-based 调度、公平共享等特性；阿里巴巴的 **Koordinator**<sup>[6]</sup> 侧重在线离线混部场景，通过 QoS 感知调度、资源超卖机制提升集群整体利用率。这两个项目均延续了 kube-scheduler 的单实例架构，通过在插件层面扩展 K8s 原生调度器实现差异化能力，其**性能扩展性受制于单实例架构本身**。

**（三）大规模一致性方向。** 学界与业界均意识到分布式调度器需要在多实例并发场景下保持"任一 Pod 至多绑定到一个节点"这一核心不变量。Omega 论文以乐观锁 + 冲突重试的方式给出答案，而工业界的实现（包括 Gödel）则更多依赖 Kubernetes API Server 的事务语义。然而，围绕分区调度器**在节点归属动态变更场景下**的严格一致性保证，公开发表的完整分析仍然罕见。

综合来看，现有研究的**局限性**主要体现在以下三方面：

1. **分布式调度器的公开评估维度单一**：Gödel 等分布式调度器的公开评估多聚焦于稳态吞吐指标，缺乏在延迟分位数、绑定成功率、资源开销等维度的系统性对比；
2. **独立 Binder 部署形态的开销缺乏定量分析**：Binder 组件作为独立 Deployment 引入的跨进程通信开销、序列化开销、事件传递延迟，尚未有公开研究给出量化数据；
3. **绑定阶段的容错机制缺乏结构化设计与证明**：分布式调度场景下节点归属漂移、Bind API 暂态失败、跨实例失败回退等边界场景，尚未见完整的分层容错机制、严格的不变量证明与开源实现。

上述三点局限，也正是本文研究工作的切入点。

## 1.3 研究目标与主要贡献

针对上述现状与局限，本文围绕**大规模分布式 Kubernetes 调度器**开展系统性研究，聚焦于分布式调度场景下的架构设计、一致性保证与性能优化。研究目标包括：

- 系统性梳理分布式 Kubernetes 调度器的架构模型与基于 etcd 的一致性依赖，形成可推广的设计参考；
- 针对分区调度场景下的四类典型故障，设计并实现严格保持核心不变量的分层绑定容错机制；
- 解决现有分布式调度器中"独立绑定组件"引入的跨进程开销与串行化瓶颈，提出面向大规模的进程内绑定架构；
- 搭建可复现的多调度器基准评估平台，对本文方案与 Gödel、kube-scheduler、Volcano、Koordinator 四类主流调度器进行多维度性能对比。

本文的工程实现基于 kubewharf/godel-scheduler 开源代码库进行拓展与重构，选择该项目的原因是它是当前唯一公开完整实现"Dispatcher/Scheduler/Binder 三层分布式架构"的开源方案，其上下游生态成熟、可复现性好，便于将本文研究成果与已有工作严格对比。本文的核心贡献——分布式绑定容错机制与进程内 Binder 架构 ENO——均为原创性设计，其正确性证明、性能改进与工程实现相互独立可查（见附录代码与实验数据）。

本文的主要贡献包括：

**创新点 1：单 Dispatcher、多独立 Scheduler 分布式调度架构（ENO）。** 提出将原独立部署的 Binder 合并进 Scheduler 进程的架构改造，构建"单 Dispatcher 统一分发 + 多 Scheduler 独立并行执行"的协同模型，使系统整体吞吐能力可随 Scheduler 实例数近线性扩展。设计并实现了 CacheAdapter 共享缓存适配层，使 Scheduler 与进程内 Binder 通过对象引用共享同一份 SchedulerCache 内存实例，实现零拷贝、零同步延迟的状态复用。相比独立 Binder 部署形态，ENO 消除了跨进程 API 往返与相应的序列化开销。

**创新点 2：基于 etcd 语义的分层绑定容错策略。** 针对分布式调度中最易被忽视的绑定阶段异常，构建四层结构化容错链路：**节点分区验证（Layer 0，预防层）**通过 Bind 前置校验拦截节点归属漂移；**同步指数退避重试（Layer 1，即时恢复层）**处理 apiserver 暂态错误；**异步 Reconciler 队列（Layer 2，后台恢复层）**清理孤儿 Assumed 状态；**Dispatcher 跨实例回退（Layer 3，全局恢复层）**通过清理 `scheduler-name` 注解触发全局重分发。四层机制形成本文所见分布式 Kubernetes 调度系统中首个结构化的绑定容错模型，并给出了核心不变量"任一 Pod 至多绑定到一个节点"的完整证明要点，明确了每一层如何依赖 etcd 的原子性语义维护不变量。

除上述两项核心创新外，本文还构建了**可复现的多调度器大规模评估平台**作为辅助工作产出：基于 KWOK 仿真环境搭建了包含 1000 节点与 5000 节点两种规模、两种工作负载共 60 次实验的评估平台，对本文方案与 Gödel、kube-scheduler、Volcano、Koordinator 四个基线在稳态吞吐、P90/P99 调度延迟、绑定成功率、goroutines 资源开销等维度进行了系统性对比，并公开完整的实验方法学与原始数据，为后续研究提供可复现基线。

## 1.4 论文组织结构

本文共分七章，结构如下：

**第一章 绪论**，即本章，介绍研究背景、国内外研究现状、研究目标与主要贡献，以及论文组织结构。

**第二章 相关工作与背景**，梳理 Kubernetes 原生调度器、Volcano、Koordinator、Gödel 四种代表性调度器的架构与特点，并简要介绍 etcd 的一致性模型与本文关键依赖的原子性语义。

**第三章 分布式 Kubernetes 调度器系统架构**，系统阐述 Dispatcher/Scheduler/Binder 三层架构、节点分区机制、以及基于 etcd 的三步事务写入模型（dispatching → assuming → binding），并配合三张原创系统图分别展示总体架构、Dispatcher 内部流程、单个 Scheduler 内部流程。

**第四章 基于 etcd 语义的一致性容错机制**，是本文的核心章节之一，详细展开四层容错机制的设计、实现与不变量证明。

**第五章 面向大规模场景的架构优化（ENO）**，阐述独立 Binder 到进程内 Binder 的架构改造思路、Cache 零拷贝共享机制、部署形态变化，以及 CLI 开关的可切换性设计。

**第六章 实验设计与评估**，介绍实验环境、工作负载、评估指标，并给出 ENO 与四种基线调度器的对比结果分析。

**第七章 总结与展望**，回顾主要贡献，诚实讨论工作的局限性，并展望后续研究方向。

# 第七章　总结与展望

## 7.1　工作总结

本文以"基于 etcd 的分布式 Kubernetes 调度器研究与实现"为题，围绕多实例并发调度场景下的一致性保证与大规模性能优化两个核心问题展开研究。以字节跳动开源的 Gödel Scheduler 为基础平台，完成了架构梳理、机制设计与性能优化三方面工作：

（1）分布式调度器架构的系统性梳理。第 3 章明确了 Dispatcher / Scheduler / Binder 三层架构下 Pod 的完整流转过程，并指出整个分布式调度器不依赖任何自研的分布式协调机制，而是完全建立在 kube-apiserver 暴露的三种 etcd 原子性语义之上：Pod / Node 注解的 `resourceVersion` 乐观并发、Watch 一致性视图、Bind 子资源的原子写入。

（2）基于 etcd 语义的多层一致性容错机制。第 4 章针对分区归属漂移、Bind API 暂态失败、Bind 失败后的 Assumed 状态残留、本地重试耗尽四类典型威胁，设计并实现了包含节点归属前置校验（Layer 0）、同步重试（Layer 1）、异步 Reconciler（Layer 2）、跨 Scheduler 实例回退（Layer 3）的四层容错框架，并给出了核心不变量"任一 Pod 至多绑定到一个节点"的完整证明。

（3）面向大规模场景的 ENO 架构优化。第 5 章提出将原独立部署的 Binder 合并进 Scheduler 进程的架构改造，通过 CacheAdapter 桥接层实现 SchedulerCache 零拷贝共享，消除了跨进程 API 调用与序列化开销，同时保持了第 4 章一致性容错机制的完整性。

第 6 章基于 KWOK 仿真在 16 个对比场景（s1~s4 × w1~w7、inst1/inst3、n=3 中位数）下将 ENO 与 Gödel、kube-scheduler、Volcano、Koordinator 逐项比对。最直接的一组读数是 s3/w3 主评估场景：inst1 下 ENO 的 P99 调度延迟由 Gödel 的 32.57 s 降到 16.22 s，inst3 下二者都进入亚秒级（0.13 s vs 0.15 s），有效吞吐提升 5.1%~21.7%。其余场景与 Gang / 突发 / 异构负载下的表现见 6.4~6.5 的完整数据。

## 7.2　主要贡献

本文有两项核心创新（与摘要及 1.3 节一致）：

- 创新点 1：单 Dispatcher、多独立 Scheduler 的分布式调度架构 ENO（第 5 章）——将 Binder 合并进 Scheduler 进程，用 CacheAdapter 做零拷贝共享消除跨进程开销，保持向后兼容与一致性保证；
- 创新点 2：基于 etcd 语义的四层绑定容错机制（第 4 章）——面向分区调度器场景下节点归属动态漂移的问题，给出了核心不变量的完整证明。

评估平台本身也作为副产出对外公开：第 6 章覆盖 s1~s4 规模、w1~w7 负载、inst1/inst3 两档实例配置的 16 个基准场景的原始数据与脚本均随本文一起开源，供后续研究复用。

## 7.3　局限性

本文有几处未覆盖的边界。第一处在 Gang 场景（w6）：ENO 的单 Pod 尾延迟高于 Gödel，本文归因于"同组预留等待与后续 Pod 的调度决策共用同一进程与队列"，但尚未通过独立的计时实验把"同组预留等待"与"调度决策 + 绑定耗时"两段耗时分离开量化验证（6.7 节第（2）条给出了这一解释未被证实的详细讨论）。

其次是生产环境。全部实验都在 KWOK 仿真下完成，去掉了 kubelet、容器运行时、真实网络与磁盘 IO 的干扰，得到的绝对数值不能直接外推到生产集群，只能作为"跨调度器相对对比"的基准。

最后是资源开销的量化。ENO 与 Gödel 的公平对比策略是"每个 Deployment 的资源规格相同"，即 Scheduler Pod 与 Binder Pod 都按 2 CPU / 4 GB 分配；这一策略在单 Pod 层面保证公平，但没有量化 ENO 因整体移除 Binder Deployment 在集群总资源开销上带来的收益。

## 7.4　未来工作

三个自然的延伸方向。第一是**真实生产环境的灰度**——KWOK 只能证明相对差距，真节点的排队、镜像拉取、网络 IO 一定会改变绝对数值和延迟长尾形态，需要在生产集群做一轮观测才知道 ENO 的收益是否维持。

第二是**多 Dispatcher 分区协同**。当前 Dispatcher 是单实例 Leader Election，对跨地域场景不够友好；把节点分区表本身也做分区化，允许多个 Dispatcher 并行维护自己的分区视图，是自然的下一步。

第三是**在 ENO 上叠加具体调度策略**。本文只做了架构与一致性层面的工作，没有涉及资源感知、拓扑亲和、拥塞控制等策略创新。ENO 的进程内 Binder + 三层容错为这些策略的实验提供了一个基础平台。

## P1 基于 etcd 的分布式 Kubernetes 调度器研究与实现

- 核心信息：硕士学位论文答辩
- 讲稿：各位老师上午好。我的论文题目是《基于 etcd 的分布式 Kubernetes 调度器研究与实现》。这项工作针对分布式调度器把绑定拆出去之后吞吐上不去、一致性也守不住的问题。一句话概括：把 Binder 合并回 Scheduler，用四层机制守住“至多绑定一次”。

## P2 研究背景

- 核心信息：生产集群进入万节点量级，单实例架构在吞吐与高可用上同时受制
- 讲稿：先说背景。Kubernetes 已成为云原生的事实标准，调度器在 Pod 生命周期的关键路径上，吞吐和延迟直接决定资源利用率与业务响应速度。千节点规模单实例还能撑住，到万节点量级就暴露三个瓶颈：activeQ 串行、Filter/Score 随规模线性、Leader 单点。

## P9 CacheAdapter

- 核心信息：
- 视觉：fig5-2-cache-zero-copy.png
- 讲稿：难点在缓存。以前 Binder 在另一个进程，缓存要么复制要么重建。CacheAdapter 让进程内 Binder 直接拿到同一份 SchedulerCache 的对象引用，所以叫零拷贝。两边看到同一份状态，Layer 0 的校验才有同一个真相可依。

## P10 四层绑定容错

- 核心信息：每一层对应一类威胁，并分别依赖一种 etcd 原子语义
- 讲稿：四层是一条时间轴。Bind 前 Layer 0 校验归属注解，非本分区直接拒绝并回退。Bind 中 Layer 1 只处理 409、429、ServerTimeout 三类暂态错误：线性退避 100、200、300 毫秒，最多三次，其它错误立即上抛。失败后 Layer 2 异步清理残留注解，按失败计数决定本地重试还是上升。重试耗尽 Layer 3 用一次原子 patch 交回 Dispatcher 重分发。
- 来源：第 4 章 §4.3~§4.6

## P11 核心不变量 I

- 核心信息：所有机制最终归约到“任一 Pod 至多绑定到一个节点”
- 要点：P1 Bind 唯一性：nodeName 为空才允许写，重复写返回 409；P2 Assumed 清理：Reject 阶段 ForgetPod，Layer 2 清 etcd 注解；P3 清理与重分发时序：一次 PatchPod 原子提交，无中间态；P4 前置拦截：归属注解 + Layer 0 校验，缓存滞后由 P1 兜底
- 视觉：fig4-3-consistency-invariant.png
- 讲稿：所有机制最后都归约到这一条不变量 I：任一 Pod 至多绑定到一个节点。证明拆四点。P1 是 Bind 唯一性，来自 Kubernetes 自身：nodeName 为空才允许原子写入，重复写返回 409。P2 是 Assumed 清理，Reject 阶段 ForgetPod 清内存态，Layer 2 清 etcd 注解。P3 是清理到重分发的时序，一次 PatchPod 原子提交。P4 是 Layer 0 前置拦截，缓存滞后由 P1 兜底。
- 来源：第 4 章 §4.2；图 4-3

## P13 评估指标

- 核心信息：
- 要点：有效吞吐：每次 run 单独算「总工作量 ÷ 完成时间」，再取 3 次中位数（不走时序聚合）；其余时序指标：3 条 run 逐点取中位（离散度半 IQR）→ 剔首尾各 2 点（约 30 s）→ 取中位数；分位数线性插值；队列堆积是例外：逐点中位聚合后取峰值、不做剔尾；c/d/e 过载存在幸存者偏差，只与 a/b 比吞吐、队列、成功率
- 讲稿：这一页是方法学核心。吞吐时序是爬升、平台、归零三段，直接取平均会被尾段零值稀释，稀释程度还取决于跑多久，跨调度器就不可比，所以主口径是总工作量除以总完成时间。时序处理三步：每个场景跑三次，按相对时间对齐后逐时间点取中位数；剔掉首尾各两个采样点，也就是约 30 秒的预热与冷却；剩下的序列上取分位数，P90、P99 用线性插值算。队列堆积是个例外，取过程最大值；绑定成功率按三次比值取中位数。c、d、e 是单实例，过载时 Pod 没进直方图，存在幸存者偏差，只做定性说明。所以跨调度器我只用吞吐、队列堆积与绑定成功率做整体比较，延迟只在 ENO 与 Gödel 之间比。这三条口径是后面所有数字可比的前提；口径不同，数字就不能直接并列。
- 来源：6.3 节；表 6-5 口径

## P14 绑定正确性与不变量验证

- 核心信息：144 次 run 的 apiserver 断言全部通过：unbound = 0 且 dup = 0
- 要点：ENO 48 次 run：绑定成功率 100%；Layer 0 / Layer 3 故障注入均通过
- 讲稿：在给性能数字之前，先说正确性。144 次 run，每次跑完都在 apiserver 侧断言：未绑定为零、重复绑定为零，全部通过；ENO 那 48 次 run 成功率都是 100%。两场故障注入各 6 项判据全过。所谓正确，不是日志里没报错，而是外部可观测的事实对得上。断言是在 apiserver 侧做的，不是调度器自报。
- 来源：6.6 节；6.7 节

## P20 归因闭环

- 核心信息：去掉一次跨进程绑定链路，换来吞吐、尾延迟、队列深度的同步改善
- 要点：相关不等于归因：峰值吞吐并非全面领先；s3/w5、s4/w3 峰值吞吐低于 Gödel；收益部分来自启动更快（口径权衡）
- 表格：机制差异 | 对应指标 | 实测证据
- 讲稿：把机制和指标对齐。进程内绑定去掉事件传递，对应 E2E 降低，三实例 0.45 对 0.93 秒；零拷贝让状态复用无同步延迟；关键是第三行，没有独立 Binder 的串行段，吞吐才能随实例扩展，+17.5% 对 +1.4%；第四行四层容错守住不变量。也要说明相关与归因的区别：峰值吞吐不是每个场景都领先。如果评委追问某个数字，备用页里有完整口径与原始目录。四行对应四个机制，每一项都有可复核的字段。
- 来源：6.4.4 节；6.8 节

## P21 故障注入 Layer 0

- 核心信息：10% 节点注解漂移，300 次拦截全部转为合规重排
- 要点：拦截 300 次 / 回退 300 次；绑定成功率 1.00；断言 50000/50000；总耗时 683 s 对基线 680 s（+0.4%）
- 视觉：fig6-29a-layer0-timeseries.png
- 讲稿：第一场注入：s2/w2、三实例，第 30 秒把 10% 的节点、约 100 个，归属注解从 scheduler-0 改为 scheduler-1。NodeValidator 拦截 300 次，Dispatcher 回退 300 次，两条曲线重叠。拦截不等于丢弃：Pod 进回退队列被重分发，成功率仍是 1.00，总耗时 683 秒、只比基线多 3 秒。这组数字说明 Layer 0 只是把错误前置，不是把工作丢掉，代价几乎为零。拦截 300 次、回退 300 次，两边对得上，说明没有 Pod 被丢掉。
- 来源：6.7.1 节；图 6-29a；表 15

## P22 故障注入 Layer 3

- 核心信息：杀掉 1/3 实例并停机 180 s，系统仍在 784 s 内完成全部绑定
- 要点：被杀实例绑定占比 68/8407 = 0.81%；存活实例接管 8407 pods；pending 353→2；总耗时 784 s，较基线 +15.3%
- 视觉：fig6-29b-layer3-timeseries.png
- 讲稿：第二场注入：第 10 秒杀掉 scheduler-0，停机 180 秒，实测中断 189 秒。被杀实例未完成的绑定只占 68/8407，即 0.81%；两个存活实例接管 8407 个 Pod，队列峰值 353 后回落到 2。累计绑定 49607/50000，断言仍全过。代价是 784 秒、比基线多 104 秒，是工作量重排的代价，不是数据损坏。对比基线是同一场景下的无故障运行，680 秒。队列在 353 之后回落到 2，说明积压是瞬时的。
- 来源：6.7.2 节；图 6-29b；表 16

## P23 局限性与威胁效力

- 核心信息：结论在“跨调度器相对比较”上成立，绝对数值不外推到生产
- 讲稿：局限六条，只讲关键。KWOK 是仿真，绝对数值不外推，但跨调度器相对比较成立。Gang 即 w6，ENO 尾延迟确实更高：吞吐高 4.3% 到 19.1%，单 Pod P99 高 1.6 到 4.1 倍，原因是同组预留等待与决策共用进程和队列。s3 到 s4 固定三实例，退化幅度不能读成上限。其余是资源公平、Volcano 口径、幸存者偏差。这六条不是免责声明，而是给结论划边界。在这个边界内，跨调度器的相对结论是稳的。
- 来源：6.8 节；6.3.3 节

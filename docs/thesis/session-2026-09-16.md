## 1. 最大发现：ENO 路径的 L2→L3 未闭环

### 1.1 事实

代码里存在**两个** Reconciler，语义不同，我此前误当作同一件事：

| 名称 | 位置 | 使用者 | 是否含 MaxLocalRetries / L3 触发 |
|---|---|---|---|
| `BinderTasksReconciler` | [pkg/binder/binder_reconciler.go](../../pkg/binder/binder_reconciler.go) | 原始独立 Binder 路径（`godel_binder.go` 的 `RejectFailedTasks`） | **有**（通过 `CleanupPodAnnotationsWithRetryCount`） |
| `FailedTaskReconciler` | [pkg/scheduler/reconciler/reconciler.go](../../pkg/scheduler/reconciler/reconciler.go) | **ENO 路径**（`unit_scheduler.go` 的 `persistViaEmbeddedBinder`） | **无**（仅做 annotation 补写重试） |

**关键事实**：
- ENO 的失败 Pod 通过 `gs.Reconciler.AddFailedTask(...)`（[unit_scheduler.go:847](../../pkg/scheduler/core/unit_scheduler/unit_scheduler.go#L847)、[:869](../../pkg/scheduler/core/unit_scheduler/unit_scheduler.go#L869)）入队，**用的是 Scheduler 侧的 `FailedTaskReconciler`**，其 worker 只做 `PatchPod` 补写 annotations，从不检查 `MaxLocalRetries`、从不清 `scheduler-name` 注解。
- `EmbeddedBinder` 里虽然构造了一个 `BinderTasksReconciler`（[embedded_binder.go:107](../../pkg/binder/embedded_binder.go#L107) 的 `eb.reconciler`）并 `Run`，但**全 repo grep 显示无任何 `AddFailedTask` 调用它**，是**死代码**。
- 累计失败计数 `BindFailureCountAnnotationKey = "eno.io/bind-failure-count"` 在 `IncrementBindFailureCount` 里被 in-memory 递增（[embedded_binder.go:209](../../pkg/binder/embedded_binder.go#L209)），但该次修改**不会经 patch 持久化到 etcd**，也不会被 ENO 的 reconciler 读取。

### 1.2 后果

- 论文 §4.4.2 / §4.5.1 描绘的"L2 达到 MaxLocalRetries → L3 触发 Dispatcher 重分发"这条路径，**在 ENO 实际运行时不会发生**。
- 一颗 Pod 若在同一 Scheduler 上反复 Bind 失败，代码里既没有失败计数持久化、也没有触发跨实例回退的机制；apiserver 稳定时会一直陷在同一 Scheduler 内重试。
- L3（Dispatcher 重分发）的实际入口路径需要重新描述，或补齐代码。

### 1.3 已回滚的错误理解

会话中我给出过若干**错误描述**，最终以代码为准更正如下：

| 我曾说 | 实际情况 |
|---|---|
| L2 worker 并发度 K 处理任务 | 单 worker goroutine（`wait.Until(worker, 1s, stop)` 的 1s 是意外退出后的重启周期） |
| L2 worker 首先调 `ForgetPod` | `ForgetPod` 在主流水线同步阶段就跑过；L2 worker 里没有该动作 |
| L2 触发 L3 靠"节点归属判据" | 靠 `MaxLocalRetries` 累计失败数；且只在 `CleanupPodAnnotationsWithRetryCount` 里检查 |
| `APICallFailedTaskQueue` 是持久化队列 | client-go 内存 workqueue，进程 panic 后队列清空 |
| ENO 路径 L2 就是 `BinderTasksReconciler` | ENO 用的是 `FailedTaskReconciler`（另一个包） |

## 3. 待定：L2/L3 实现缺口修补方向

### 方案 A —— 激活独立 Binder 侧的 reconciler（**最小侵入**）

**做什么**：让 `EmbeddedBinder` 或 `persistViaEmbeddedBinder` 在 Bind 失败时通过 `eb.reconciler.AddFailedTask(...)` 入队到 `BinderTasksReconciler`，而不是（或除了）`gs.Reconciler`。

**优点**：
- `BinderTasksReconciler` 已有 `CleanupPodAnnotationsWithRetryCount` 与 L3 触发逻辑，直接可用
- 代码变动 5-10 行，`eb.reconciler` 从死代码变活
- §4.4.2 的现有重写基本适用，改动最少

**缺点**：
- 两条重试路径并存（`gs.Reconciler` 补写 assumed-node + `eb.reconciler` 做 L3 升级）语义上有点乱，需要额外说明如何避免重复入队

### 方案 B —— 把 L3 逻辑并入 `FailedTaskReconciler`（**最合理**）

**做什么**：在 `FailedTaskReconciler` 里加 `maxLocalRetries` 字段，worker 里检查 Pod 的 `bind-failure-count` 注解，达标时清 `scheduler-name` + `PodState=Pending`；`IncrementBindFailureCount` 之后同步 patch 到 etcd（否则计数不持久化）。

**优点**：
- 只保留一条 reconciler 链路，语义清晰
- 与 ENO 的整体设计（Scheduler 内嵌 Binder）一致
- 图 4-1 状态机的 `L2_Queue → Pending` 转移终于有真实代码支撑

**缺点**：
- 需要修改 `IncrementBindFailureCount` 的调用点，让计数写回 etcd
- 需要给 `FailedTaskReconciler` 加构造参数（`maxLocalRetries` / `schedulerName`）
- 代码改动 15-25 行 + 补 unit test

### 方案 C —— 不改代码，如实描述现状（**最诚实**）

**做什么**：论文里把 §4.4/§4.5 的"ENO 路径 L3 由 MaxLocalRetries 触发"改成如实描述——L3 仅在独立 Binder 路径下工作，ENO 路径 L3 触发依赖后续实现；§7.3 局限性增加一条。

**优点**：
- 零代码风险，主实验数据零受影响
- 学术上诚实，答辩老师可以接受"实现优先级"这种解释

**缺点**：
- 摘要与第 7 章"分层容错模型"的叙述会略显打折扣
- 答辩追问"为什么 ENO 没接入 L3"时需要有理由（e.g., 优先验证 fast path 稳定性）

### 关于测试数据是否需要重跑

**不需要重跑**（论证见 [§6](#6-代码改造对已有测试数据的影响)）。已有 126 次实验的 `bind_success_rate == 100%`，意味着 L2/L3 相关代码路径**从未被跑到过**，改造这些路径不会影响任何已采集的稳态指标。

## 6. 代码改造对已有测试数据的影响

### 6.1 结论

**不需要重跑主实验数据**。

### 6.2 论证

看现有 126 次实验的元数据（`schedule_completion_rate == 1.0` 或未记录但推算 100%，`bind_success_rate == 100%`）：

- `FailedTaskReconciler.AddFailedTask` 从未被调用（因为 `bindResult.AllSucceeded() == true`）
- `bindPodToNode` 里的 3 次重试从未进入 retry 分支
- `CleanupPodAnnotations*` 系列函数从未被 worker 执行过
- MaxLocalRetries 检查代码从未运行过

**所有稳态指标（吞吐、延迟、成功率、队列堆积）建立在 happy path 上，改造的是从未被跑到的失败恢复分支。**

### 6.3 可能被间接影响的指标

| 指标 | 影响 | 处理 |
|---|---|---|
| 稳态吞吐、P90/P99 延迟、绑定成功率 | 无影响 | 无需处理 |
| goroutines 数量 | 可能 +1 或 +2（若激活 `eb.reconciler` 或新增 worker） | 若表 6-7 有精确数值，说明"稳态附近某个基线" |
| 进程内存基线 | 可能 +几 MB（多一个 workqueue 实例） | 表 6-7 无此项，无需处理 |

### 6.4 稳妥的验证步骤

改造完成后建议小规模冒烟（不重跑主实验）：

```bash
./run-all.sh --groups "a" --scales "s1" --workloads "w1" --instances "1" \
             --setup-nodes --redeploy-each-run
```

对比 `results/a/s1/w1/inst1/run{1,2,3}/avg` 里已有稳态数据的中位数，误差 <3% 即认为 fast path 无 regression。

### 6.5 需要重跑的例外情形（本次改造不涉及）

只有以下改动才需要重跑主实验：

1. 修改了 `bindPodToNode` 的 fast path（每次 Bind 都走的代码）
2. 重命名了 Prometheus metric（如 `bind_throughput_pods`）
3. 引入了新的全局锁或 cache 层重构
4. 在每次 successful bind 后引入了新的同步操作

**本次讨论的 L2/L3 改造属于纯 fallback 路径修补，不涉及以上任何一点。**

## 8. 会话中的方法论教训

诚实记录，供后续 agent 参考：

1. **涉及"分层机制怎么触发"这类问题，应先做调用图（谁 AddFailedTask、谁跑 worker、worker 写哪个 API），再答**。会话中我几次基于 helper 函数（`CleanupPodAnnotations*`）倒推"谁在用"，遗漏了 `FailedTaskReconciler` 与 `BinderTasksReconciler` 是两条独立链路的事实，直到用户追问才 grep 验证。
2. **grep manifests 是排除 webhook 假说的第一步，不是最后一步**。会话中我推了两次 webhook 假说，最后 grep `manifests/` 发现 ENO/Gödel 没有 admission webhook 才排除。
3. **"1s worker 兜底重启"不是"1s 并发度 K"**。看 `wait.Until` 的 signature 就知道，我一开始误读了。
4. **"死代码"要注意**——`eb.reconciler` 就是典型例子：构造 + Run 齐全，但没有 `AddFailedTask` 调用。看 goroutine 是否真被喂数据，比"字段是否存在"更能判断代码是否活着。

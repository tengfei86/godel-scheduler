## 1. 研究背景与问题
- kube-scheduler 单实例串行架构存在三个瓶颈：吞吐存在上限；P99 延迟随节点规模上升；Leader Election 单活跃部署存在单点故障。
- Gödel Scheduler 通过 Dispatcher/Scheduler/Binder 三层解耦与节点分区实现并发调度，是代表性开源分布式实现。
- 其不足：独立部署的 Binder 在超高并发下重新引入绑定串行化瓶颈与跨进程通信开销；节点分区归属动态漂移场景下的严格一致性仍缺乏完整论证。
- 本文两个核心问题：
  Q1（性能）：如何消除独立 Binder 带来的跨进程绑定瓶颈，使吞吐随实例数扩展？
  Q2（一致性）：在分区归属动态漂移时，如何保证“任一 Pod 至多绑定到一个节点”？

## 2. 方案与创新
创新点 1：单 Dispatcher、多独立 Scheduler 的 ENO 架构（第 5 章）
- 将 Binder 合并进 Scheduler 进程，使绑定执行链路与调度决策实例同域化；
- 通过 CacheAdapter 共享缓存适配层，让 Scheduler 与进程内 Binder 共享同一份 SchedulerCache 实例，实现零拷贝状态复用；
- 消除 Scheduler → Binder 的事件传递、跨进程 API 调用与序列化开销；
- 保留 CLI 开关，可在“独立 Binder / 进程内 Binder”两种形态间切换，保证向后兼容。

创新点 2：基于 etcd 语义的四层绑定容错机制（第 4 章）
- Layer 0 节点归属前置校验（预防层）：Bind 前校验 Node 的 eno.io/scheduler-name 注解，拦截分区归属漂移；
- Layer 1 同步指数退避重试（即时恢复层）：处理 apiserver 暂态错误；
- Layer 2 异步 Reconciler 队列（后台恢复层）：回收孤儿 Assumed 状态；
- Layer 3 跨 Scheduler 实例回退（全局恢复层）：本地重试耗尽后，由 Dispatcher 清理 scheduler-name 注解并触发全局重分发。
- 核心不变量 I：任一 Pod 至多绑定到一个节点。
- 论文给出不变量 I 的完整证明要点，并明确四层机制分别如何依赖 etcd 的三种原子性语义：
  ① Pod/Node 注解的 resourceVersion 乐观并发；② Watch 一致性视图；③ Bind 子资源的原子写入。

## 3. 实验设置
- 平台：KWOK（Kubernetes WithOut Kubelet）仿真，kind 集群内运行，Kubernetes v1.34.8；单机 64 vCPU / 128 GB。
- 规模：s1=100 节点，s2=1000，s3=5000，s4=10000。
- 负载：w1=100 pods/s（10,000 pods）；w2=500 pods/s（50,000）；w3=1000 pods/s（100,000）；w4=2000 pods/s（200,000，极限）；w5=0→2000→0 pods/s（50,000，突发）；w6=200 组/s×5 pods（50,000，Gang）；w7=500 pods/s（50,000，异构资源）。
- 实例配置：inst1（1 实例）与 inst3（3 实例）。
- 对比组：a=ENO（本文）；b=Gödel（原生）；c=kube-scheduler v1.34.8；d=Volcano；e=Koordinator。
- 实验规模：16 个对比场景；每个场景重复 3 次；结果目录共 144 次 run；统计口径为 n=3 中位数。
- 公平性：各调度器 Pod 统一 requests 2 CPU / 4 GB、limits 4 CPU / 8 GB；Scheduler 客户端 QPS 与 Burst 均为 10000。
- 观测栈：Prometheus 15 s 抓取 + recording rules 归一化；Grafana 可视化；负载前 30 s warmup、结束前 30 s cooldown 剔除。

## 4. 评估指标（第 6 章重点）
论文从性能与稳定性两个维度评估，共 6 个指标：
1. 有效吞吐（pods/s）= 名义总工作量 ÷ 总完成时间（duration）。这是本文吞吐的主口径，与采样窗口长度无关。
2. 峰值吞吐（pods/s）= scheduling_peak_throughput，处理过程中的最高瞬时调度速率。
3. P90 / P99 调度延迟（s）= 从 Pod 进入 activeQ 到完成 Bind 的分位延迟。
4. Pod E2E 延迟 P99（s）= pod_e2e_latency_p99，从 Dispatcher 观察到 Pod 直至绑定完成。
5. 绑定成功率 = Bind 成功次数 / Bind 尝试次数。
6. 队列堆积峰值（pods）= pending_pods 在处理过程中的最大值。

指标口径要点（必须在 PPT 中讲清）：
- 吞吐原始时序呈“爬升—平台—归零”三段结构，直接取均值会被尾段零值稀释，且稀释程度依赖实验时长，因此采用“有效吞吐”作为主口径。
- 时序类指标先对 3 条 run 逐时间点取中位数，再剔除首尾各 2 个采样点（约 30 s），然后取标量。
- 跨调度器延迟对比的方法学限定：c/d/e 为单实例，过载时大量 Pod 堵塞在 activeQ、从未进入 latency histogram 采样窗口，存在幸存者偏差（Survivor Bias）；因此 a vs b 可直接比较延迟（同源指标），与 c/d/e 只用吞吐、队列堆积、绑定成功率做整体对比，不直接对齐 P99 数值。

## 5. 正确性结果
- ENO 在 16 个场景 × 3 次 = 48 次 run 中，绑定成功率始终 100%。
- 全部 144 次 run 的 apiserver 断言均为 unbound = 0 ∧ dup = 0，核心不变量 I 严格成立。
- Layer 0 故障注入（s2/w2/inst3，T+30 s 将 10% 节点即约 100/1000 个节点的 eno.io/scheduler-name 从 scheduler-0 改为 scheduler-1）：
  6 项判据全部通过；NodeValidator 拦截 300 次；Dispatcher 回退 300 次；绑定成功率 1.00；不变量断言 50000/50000；总耗时 683 s，较无故障基线 680 s 仅 +3 s（+0.4%）。
- Layer 3 故障注入（s2/w2/inst3，T+10 s 杀掉 scheduler-0，停机 180 s，实测 outage 189 s）：
  6 项判据全部通过；dispatcher_orphan_pods_reset 触发 77.15 events/s；被杀实例绑定占比 68/8407 = 0.81%；存活实例接管 8407 pods；pending 峰值 353 后回落至 2；累计绑定 49607/50000；不变量断言 50000/50000；总耗时 784 s，较基线 +104 s（+15.3%）。

## 6. 性能结果
### 6.1 五组基线（场景 1~5，inst1，n=3 中位数，有效吞吐 pods/s）
| 场景 | ENO | Gödel | kube-scheduler | Volcano | Koordinator |
|---|---|---|---|---|---|
| s1/w1 | 90.1 | 90.1 | ≈97 | ≈48 | ≈24 |
| s2/w2 | 331.1 | 324.7 | ≈270 | ≈48 | ≈24 |
| s2/w3 | 352.1 | 286.5 | ≈297 | ≈48 | ≈16 |
| s3/w2 | 328.9 | 273.2 | ≈270 | ≈48 | ≈24 |
| s3/w3 | 297.6 | 283.3 | ≈292 | ≈48 | ≈24 |
- 三档差异：ENO/Gödel 第一档；kube-scheduler 第二档；Volcano ≈48 pods/s、Koordinator ≈24 pods/s，几乎不随规模变化。
- ENO 较 kube-scheduler 高 +1.8%~+22.5%（主评估四场景）；较 Volcano 与 Koordinator 分别高约 6 倍与 12 倍以上。
- 唯一例外：s1/w1 低负载下 ENO 较 kube-scheduler 低 7.2%，因未饱和、完成时间由注入速率决定。

### 6.2 ENO vs Gödel（16 场景）
- 有效吞吐：14 个场景领先、2 个持平（s1/w1、s4/w7）；提升幅度 +2.0%~+22.9%，平均 +11.9%。
- 亮点：s2/w3 +22.9%（352.1 vs 286.5）；s3/w3 inst3 +21.7%（349.7 vs 287.4）；s3/w5 inst3 +21.3%；s3/w7 inst3 +21.2%。
- 峰值吞吐：12 个场景领先，提升 0.2%~68.0%；s4/w6 inst3 达 +68.0%（893.2 vs 531.6）；Gödel 领先 2 个场景（s3/w5 -10.4%、s3/w6 -2.0%）。
- P99 调度延迟：除 s2/w2 外的 11 个非 Gang 场景均低于 Gödel，改善 0.3%~82.9%。
  代表值：s2/w3 23.48 s → 4.00 s（-82.9%）；s3/w3 inst1 32.57 s → 16.22 s（-50.2%）；s3/w4 inst3 -49.7%；s4/w3 inst3 -33.4%。
- Pod E2E P99：12 个非 Gang 场景均不高于 Gödel，改善 0.6%~75.3%；s2/w3 -75.3%；s3/w7 inst3 -68.2%；s3/w5 inst3 -53.8%；s3/w3 inst3 -51.9%。
- 反向情形：w6 Gang 场景 ENO 的有效吞吐仍高（+4.3%~+19.1%），但单 Pod P99 尾延迟高出 1.6~4.1 倍；论文将其归因于“同组预留等待、绑定调用与后续调度决策共用同一进程与队列”，并明确列为局限。

### 6.3 扩展性
- 实例数 inst1 → inst3（s3/w3）：
  ENO 有效吞吐 297.6 → 349.7（+17.5%）；Gödel 283.3 → 287.4（+1.4%）。
  ENO 峰值吞吐 858.2 → 1023.1（+19.2%）；Gödel 752.8 → 999.5（+32.8%）。
  P99：ENO 16.22 → 0.13 s（-99.2%）；Gödel 32.57 → 0.15 s（-99.5%）。
  Pod E2E P99：ENO 16.22 → 0.45 s（-97.2%）；Gödel 32.50 → 0.93 s（-97.1%）。
  队列堆积峰值：ENO 14698 → 20；Gödel 22652 → 16。
  结论：两者延迟都数量级下降；但 ENO 把新增并发较完整地转化为端到端速度，Gödel 的增量被独立 Binder 的串行绑定吸收。
- 规模 s3 → s4（w3/inst3，实例数不变）：
  ENO 有效吞吐 349.7 → 296.7（-15.2%）；Gödel 287.4 → 280.9（-2.3%）。
  ENO P99 0.13 → 0.19 s（+46.2%）；Gödel 0.15 → 0.28 s（+86.7%）。
  即便回落，ENO 仍领先：吞吐 296.7 vs 280.9（+5.6%）；P99 0.19 vs 0.28 s（低 33.4%）；队列堆积峰值 9 vs 61。
- 复杂负载：
  w4 极限：s3 +9.3%、s4 +16.0%；P99 低 49.7% / 14.8%；E2E 低 32.6%~35.3%。
  w5 突发：s3 +21.3%、E2E 低 53.8%；s4 +2.8%、延迟基本持平。
  w6 Gang：吞吐 +19.1%（s3/inst1）、+4.3%（s3/inst3）、+18.6%（s4/inst3）；尾延迟反向（见上）。
  w7 异构：s3 +21.2%、E2E 低 67.6%；s4 基本持平。

### 6.4 性能归因（数据与机制的闭环）
- 进程内 Binder 消除了原架构中 Scheduler → Binder 的事件传递与跨进程绑定调用（第 5 章 §5.1 步骤 ④）。
- CacheAdapter 零拷贝共享同一 SchedulerCache，避免状态复制与同步延迟。
- 直接证据链：
  ① inst1→inst3 时 ENO 吞吐 +17.5% 而 Gödel 仅 +1.4%；
  ② s3/w3 inst3 下 E2E P99 0.45 vs 0.93 s（低 51.9%）；
  ③ P99 在 11 个非 Gang 场景全面领先，s2/w3 降低 82.9%；
  ④ 队列堆积峰值 inst3 下 20 vs 16，且 s4/w3 下 9 vs 61。
- 诚实补充：有效吞吐把“稳态处理速率”和“启动/爬升速度”合并，峰值吞吐并非每个场景都领先（如 s3/w5、s4/w3），说明收益部分来自更短的整体完成时间；该口径权衡在局限性中说明。

## 7. 局限性（必须保留，体现学术严谨）
1. KWOK 仿真无法完全反映真实资源竞争、网络与磁盘 IO，绝对数值不可直接外推到生产。
2. Gang（w6）场景下两种架构的延迟入计口径不同质，ENO 尾延迟偏高，尚未通过独立计时实验分离“同组预留等待”与“调度+绑定耗时”。
3. s3→s4 对比固定 3 实例，规模翻倍未同步扩容，ENO 在 s4 的吞吐回落与该设定有关。
4. 资源公平性采用“每 Deployment 同规格”，对 ENO 略不利；ENO 移除 Binder Deployment 带来的集群总资源收益未量化。
5. Volcano 指标的测量对象、起止边界、统计粒度与其他调度器不完全等价，仅做量纲对齐。
6. c/d/e 的延迟分位数存在幸存者偏差，本文不将其与 a/b 直接数值对齐。
7. 有效吞吐口径合并了启动段与稳态段，无法拆分收益来源。

1. **先投喂论文正文**：把 `docs/thesis/chapters/06-evaluation.md` 全文、`00-abstract.md`、`07-conclusion.md` 一并附上，效果优于只给本 Prompt。
